0작업 원칙

먼저 합의해야 하는 룰을 못박고 시작합니다. 이후 모든 결정은 이 4가지를 기준으로 판단합니다.

① 코드는 ml 폴더 안에서만

  • 참고 노트북: b_classifier/i_naive_bayes_task_강사.ipynb (NB + Pipeline + LabelEncoder 패턴)
  • 보조 참고: b_classifier/h_naive_bayes.ipynb(이론), d_cross_validation.ipynb(검증)
  • 저장 패턴: b_classifier/feeling_model.pkl + feeling_encoder.pkl 쌍
  • 외부 새 라이브러리 도입 ✗ (sklearn / pandas / numpy / matplotlib / pickle / requests / BeautifulSoup4 한도 내)

② 데이터: 크롤링 우선 → 합성 보조

  • 1순위: 공개 데이터셋 (라이선스 OK인 것)
  • 2순위: 국내 커뮤니티 댓글 크롤링 (BeautifulSoup4)
  • 3순위: 부족할 때만 1·2를 기반으로 변형/확장 (자모 분리 우회·반복 음절 등)
  • 합성 데이터 비율은 전체의 30%를 넘지 않도록 제한 (편향 방지)

③ 작업 위치 단일화

  • 모든 코드는 task/classifier_task.ipynb 한 파일에 셀 단위로 작성
  • 데이터는 task/datasets/ 디렉터리에 raw / clean / split 단계별 저장
  • 최종 산출물은 task/artifacts/에 pkl + 리포트 png

④ 분류 문제로만 정의

  • 회귀(점수) 사용 ✗ — 라벨은 모두 이산값
  • 경계가 애매하면 다중분류로 풀고, 임계치는 predict_proba로 후처리
  • 다중분류는 stratify split + class_weight 또는 under-sampling으로 불균형 처리

1데이터셋 설계안 — 3가지

컬럼/타겟의 결을 다르게 한 3가지 안. 포트폴리오는 안 B(다중분류)를 메인으로 진행하고, 안 A·C는 비교군으로 부록에 수록하는 것을 권장합니다.

안 A · 이진 분류 — clean / abusive

단순 베이스라인 정보량 적음

스키마

컬럼타입설명 / 예시
idint행 고유번호 (자동증가)
textstr채팅 원문 — "ㅎㅇ 뭐해?", "ㅅㅂ 진짜 짜증나"
sourcestr출처 (crawl_dcinside / crawl_youtube / synthetic / public_kbully …)
labelstr타겟: clean | abusive

장점: 라벨링 비용↓, 베이스라인 정확도↑. 단점: "혐오 vs 단순욕"을 구분 못 해 신고 자동화에 약함.

안 B · 다중 분류 — 5클래스 권장

서비스 적합 신고 트리아지 연동 가능 불균형 주의

스키마

컬럼타입설명 / 예시
idint행 고유번호
textstr채팅 원문 (전처리 전)
text_cleanstr전처리 후 (소문자화·자모정규화·반복문자 축약·URL/이모지 토큰화)
lengthint전처리 후 길이 (분포 분석용, 학습엔 미사용 또는 별도 피처)
sourcestr출처
labelstr타겟: clean · profanity(일반욕) · hate(혐오/차별) · sexual(성적) · spam(광고/도배)

왜 이 5개? 우리 tbl_report.target_type이 post/member라 사유는 reason text에 자유서술인데, 운영팀이 처리 우선순위를 매길 때 자주 쓰는 5축이 위와 같습니다. hate는 정지, profanity는 경고, spam은 자동 숨김처럼 후속 액션이 다르게 매핑됩니다.

불균형 처리: clean이 압도적으로 많을 것 — under-sampling으로 클래스당 N개씩 균등화 (i_naive_bayes_task의 anger/fear/joy/love/sadness 1482개씩 패턴 그대로 차용).

안 C · 강도(severity) 분류 — 3클래스 ordinal

필터 강도 조절에 유리 라벨링 일관성 어려움

스키마

컬럼타입설명 / 예시
idint행 고유번호
textstr채팅 원문
categorystr보조 라벨 (안 B의 5클래스) — 분석/필터링용, 학습 타겟 ✗
severitystr타겟: none · mild(경미) · severe(심각)

사용 예: 사용자 설정 "비속어 필터 강도(약/중/강)"를 severity로 매핑. ordinal이지만 분류 모델로 풀고, 후처리에서 mild→severe 순서를 보장.

최종 권장

안 B를 메인 모델로 학습 → 부록에 안 A(이진)와 안 C(강도)를 동일 데이터로 비교 학습한 결과 표 1장 추가. 포트폴리오 스토리: "같은 데이터로 라벨 정의를 바꿨을 때 정확도/혼동행렬이 어떻게 달라지는가" — 라벨 설계 역량을 보여줄 수 있음.

2-3. 합성 (3순위 · 부족분만)

  • 변형 규칙: 자모 분리(욕→ㅇㅛㄱ), 반복(ㅅㅂㅂㅂㅂ), 특수문자 끼워넣기(시*발), 띄어쓰기(시 발), 영문 치환(siba)
  • 금지: 학습 셋에서 변형 규칙으로 만든 데이터를 검증 셋에도 넣기 ✗ — leakage 발생
  • 비율 상한: 클래스당 합성 데이터 비율 ≤ 30%. 그 이상이면 모델이 합성 패턴만 학습.

3현재 DB 테이블 활용 계획

신규 테이블 추가 없이 기존 테이블만으로 학습/추론 흐름 설계. 운영 환경에서 모델이 채팅을 어떻게 잡아먹고, 결과가 어디에 쓰일지 명시합니다.

3-1. 학습 데이터로 끌어올 후보 컬럼

테이블컬럼활용 방식
tbl_messagecontent핵심 — 본문 텍스트. 학습 입력 X.
tbl_messageid, created_datetime샘플링/시계열 분포 분석용 (모델 입력 ✗)
tbl_messageis_deletedtrue인 메시지는 신고/관리자 삭제 가능성 ↑ → 약한 라벨(weak label)로 활용 후 수동 검증

tbl_reportreason키워드(욕설/혐오/광고) 추출하여 multi-class 약라벨 부여

약라벨(weak label) 전략

운영 초기엔 라벨링 인력이 없으니 tbl_report.status='applied' AND target_type='post'인 메시지를 모아 profanity/hate/sexual/spam 후보로 분류 → 사람이 빠르게 검수 → 골드 셋 1,000건만 확보해도 NB는 충분히 학습됨.

왜 이 순서?

강사 노트북(i_naive_bayes_task_강사.ipynb)의 spam → feeling 흐름과 동일한 골격이라, 면접관이 "어디서 차용했는지"가 한눈에 보입니다. 그 위에 15·18번 회고는 사고 깊이를 보여주는 가산점 셀.

5검증 / 평가 계획

주 평가지표

  • macro F1 — 클래스 불균형이 있어도 공정. 주 의사결정 지표.
  • per-class recall — hate/sexual은 놓치면 비용↑ → recall 최소 0.7 목표
  • clean precision — 정상 메시지를 욕설로 잘못 잡으면 UX 파괴 → precision 0.95 목표

검증 방법

  • train/test stratified split (7:3)
  • cross_val_score(cv=5, scoring='f1_macro')
  • 혼동행렬 heatmap → 클래스 간 혼동 패턴 보고
  • 오분류 30건 정성 분석 → 데이터 보강 우선순위 결정

합격선 (포트폴리오 기준)

  • macro F1 ≥ 0.75 (베이스라인 NB 기준 충분히 달성 가능)
  • 혼동행렬에서 clean ↔ hate 오분류 ≤ 5%
  • 실사용 데모 10문장 중 직관과 8개 이상 일치

실패 시 대응 (계획만)

  • 데이터 부족 → 크롤링 추가, 합성 비율 조정
  • 특정 클래스 recall 낮음 → class_weight 또는 over-sampling
  • NB 한계 도달 → 동일 데이터로 LogisticRegression 비교(같은 sklearn, 동일 폴더 범위)
